# 深圳家教接单平台：项目交接手册

这份文档用于跨 Codex 窗口、账号和开发人员交接。新任务必须先完整阅读本文，再检查当前 `main` 的代码、测试和相关专项文档。本文记录产品意图和现行约束，但任何实现事实仍以仓库当前代码为准。

## 一、产品定位与设计原则

- 网站是完整主系统，面向深圳家教订单的共同上传、识别、去重、浏览、筛选和地图看单。
- 普通看单用户打开即用，不注册、不登录；匿名设备身份和个人偏好保存在浏览器。
- 手机端是重要使用场景，同时保证 PC 连续粘贴、TXT 拖入和管理操作足够高效。
- 快速、高效、稳定高于功能数量。低使用率、逻辑复杂或持续消耗资源的功能可以主动建议删除，但未经用户确认不要自行改变业务。
- 页面应当简洁、直觉，尽量让用户不看解释也知道如何使用。避免重复标题、大段说明、无价值按钮和多余状态。
- 真实等待必须有及时、明显且准确的反馈，例如正在加载订单、计算距离、已进入队列、正在识别、发布成功或无有效订单。不能让内容无反馈地消失，也不能用虚假进度安慰用户。
- 网站配色使用与高德协调的浅灰白、地图蓝和路线绿；全站通过 `prefers-color-scheme` 自动跟随系统浅色/暗色，高德地图保持其原生地图主题。
- 卡片、筛选、管理端和登录页使用统一视觉语言。品牌左上角标识已由黄色改为地图蓝+路线绿。

## 二、用户端核心体验

### 信息列表

- 默认首页是信息列表；刷新普通页面回到信息列表。管理员会话刷新后保持管理端。
- 列表加载时显示真实阶段反馈，包括正在加载订单和正在计算距离，避免空白等待。
- 筛选针对全部已加载订单，不只是当前画面中的卡片。
- “只看附近”表示距“我的位置”直线距离 10 公里以内，控件紧跟位置输入区域。
- 选择“我的位置”候选后自动显示订单直线距离，不保留额外的“显示直线距离”或“清除”按钮。
- 默认评分排序中课时费与直线距离各占 50%；没有可靠距离时按共享评分规则降级处理。
- 订单卡片可查看地图、查看原文和申请接单。列表页应保持轻量，不能为了弹窗提前拉取所有发单人联系方式。

### 申请接单

- 点击“申请接单”后才通过只读接口获取该订单关联的发单人资料，避免拖慢列表首屏。
- 弹窗先显示“联系管理员吴老师”，再显示“联系发单人”。吴老师的公开联系方式以页面现有常量为准，不在文档中重复手机号字面量。
- 两类联系方式都可点击复制，并提示“备注接单”。
- 弹窗支持查看原文、复制原文，并提示“复制原文后自行在微信里搜索”。原始订单通常来自微信，老师可先搜索原文；找不到时再联系发单人或吴老师。
- 联系方式只在用户主动申请接单后返回，不提前出现在普通订单列表响应中。

### 地图看单

- 地图支持订单标记、聚合、聚合点展开、订单与列表互跳、总览全部订单和“我附近的订单”。
- 选择“我的位置”后在地图上使用特殊标记；“我附近的订单”以该位置为中心，视野约覆盖 10 至 15 公里。
- 从订单点击“查看地图”时直接展示对应路线，视野应完整包住路线并让路线占据合理画幅。
- 地图实例在信息列表、地图和发单页切换间复用，避免每次返回地图都重新加载 SDK、底图和标记。
- 顶部视图切换采用直接切换，不再人为写入复杂的浏览器历史。此前“手机返回先回信息列表”的定制历史逻辑会造成点击信息列表失效，已删除，稳定性优先。

## 三、发单准入与身份

- 发单不是完全公开能力。首次进入发单页需填写称呼和微信号/手机号，并联系吴老师，备注“发单”。
- 管理员在“发单审核”中批准后，后端才允许该身份解析、导入和发布订单。
- 发单身份由称呼和联系方式恢复。用户在其他浏览器或设备填写完全相同的信息，可以恢复已批准身份及其订单，不会生成重复申请。
- 管理端审核列表中联系方式可点击复制；支持批准和拒绝。
- 每个新订单保留发单者身份关联。普通列表不公开该信息，只有用户点击“申请接单”后才返回称呼与联系方式。
- 发单归属不是社交展示，不做公开账号体系、在线账号密码业务或复杂个人主页。管理端账号与密码业务逻辑已删除，管理员鉴权本身仍保留。

## 四、粘贴、TXT 与解析队列

- 发单主入口标题为“粘贴并识别订单”，右侧“识别结果”与其同字号、同层级、同高度。
- 输入框主要服务一次性粘贴，但手机端允许正常输入，不能用 `readonly` 或拦截方式破坏系统粘贴菜单。
- 粘贴事件发生后，文字应短暂停留以建立视觉确认，随后立即进入顺序队列并清空输入框；无论新增、重复或无效，输入框最终都应清空。
- 快速连续粘贴时，每一批独立入队并按顺序处理，不能并发覆盖结果。连续内容之间按至少一个空行的语义切割。
- 入队反馈要快且明显：输入区产生短促成功动效，并显示已粘贴、队列批数、正在切割识别、正在发布等状态。
- 手动逐字输入允许存在；内容不完整时由解析器过滤，并提示“输入的信息不完整，请直接粘贴”，不能持续轮询空输入框或反复弹提示。
- TXT 入口位于粘贴框下方，与主输入框等宽但更矮；PC 支持点击选择和直接拖入 `.txt`。
- 网页粘贴/TXT 单批前端上限为 2 MiB，Worker 对整个 HTTP 请求另有 10 MiB 上限；兼容桥接接口的单条剪贴板上限为 512 KiB。不要在 UI 中引入比后端更松的假承诺。
- 识别过程先由共享解析器切割、分类和结构化，再在导入端去重。重复订单必须在调用高德前过滤，以节省 POI 配额。
- 识别结果按批次保留在页面中，最新批次在最上面，旧批次向后累积，由用户主动清空；不要识别后立即清掉。
- 识别结果阶段只展示文本解析结果，不调用高德。只有真正进入 `/api/import` 的新增订单才进行地点搜索、确认并发布。因此“识别 8 条、重复 8 条”应产生 0 次订单地点 POI 请求。
- 无效文本要明确提示；重复订单要准确显示“识别多少条、重复多少条、没有新增订单”；发布失败时保留队列或结果，便于重试和检查。

## 五、解析、地点与去重

- `TutorPlatform/parser/` 是订单切割、非订单分类和字段解析的唯一实现。UI、EXE、地图模块不得复制解析正则或业务逻辑。
- 地址是订单最重要的解析字段。课酬、老师条件等细节可持续优化，但不得以牺牲地址准确性和稳定性为代价。
- 文本解析必须快速返回；识别结果中的地址来自原文解析，不等于高德 POI 标准名称。
- 新订单在导入阶段由服务端调用高德地点候选，保存 POI、标准地址和经纬度；后续地图、距离和路线尽量复用已保存坐标。
- 已有地点文字但没有确认坐标的历史订单，在管理端标记“地点坐标未确认”，管理员可点击“重新识别地点”调用高德并持久化结果。
- 异常订单按明确原因打标签，不得把所有异常笼统归为“地点未确认”。异常面板用于让管理员快速复核原文、缺失字段和地点状态。
- 信息列表和发单识别结果均提供一键“识别有误”。不要求用户选择错误类型或填写说明；反馈不影响订单展示，管理端按目标合并人数并保留原文、识别快照和解析器版本。管理端一个按钮同时保存固定文件名的 JSONL/TXT；桌面 Chrome 可选择目录并覆盖同名文件，两个文件写入成功后清理已导出的反馈，导出期间新增或更新的反馈继续保留。
- 去重使用原文规范化、订单编号和语义指纹等共享规则。去重是核心数据质量边界，新入口不能绕过。
- 开放订单在三天后按上海时区定时清理。
- 当前只收集用户主动点击“识别有误”的反馈快照，不自动判断标签或训练模型。后续建立解析样本集时仍需单独设计匿名化、授权、版本和测试集隔离。

## 六、管理端当前范围

- 管理端包含：累计访客、实时在线、平台侧高德调用量、发单审核、异常订单和订单管理。
- 累计访客按浏览器 `localStorage.tutorPlatformVisitorId` 去重；清除浏览器数据或更换浏览器会被视为新访客。
- 实时在线统计最近 90 秒内发送过可见页面心跳的访客；心跳每 30 秒一次，只更新活跃时间，不增加总访问量。
- 公共“总访问量”是页面打开次数，刷新会增加；它与管理端“累计访客”不是同一指标。
- 高德调用统计来自平台实际发出的请求，按日期、接口和结果聚合，显示当天总量、当月 POI、当月基础 LBS 和限流/超额次数。它不等同于高德官方账单，最终额度以高德控制台为准。
- 订单管理只保留单条删除和批量删除。重新发布、下架、开放、关闭、已成交、申请人数等状态和按钮均已删除。
- 已删除：平台公告、平台设置、问题反馈业务、网页端账号密码业务、无价值的订单状态流转。
- 管理端订单卡片与信息列表卡片保持相同视觉语言，信息密度可更高，但避免独立做一套粗糙样式。

## 七、高德地图配置与容量边界

详细调用表见 [AMAP_AUDIT.md](./AMAP_AUDIT.md)。三项配置职责不同，不是三个可轮换的同类 Key：

- `AMAP_WEB_SERVICE_KEY`：服务端地点搜索、地理编码和路线 REST API。
- `AMAP_JS_API_KEY`：浏览器加载地图、标记聚合和 JS 路线插件。
- `AMAP_JS_SECURITY_CODE`：JS API 2.0 安全密钥，仅由 Worker 同源代理使用，不直接返回浏览器。

当前服务端设有最多 4 个高德并发请求、相同请求合并和短期缓存，并对限流做有限重试。约 200 名老师的早期规模应先使用单个已认证账号并监控真实数据，不要通过多个个人账号做轮换池规避配额。规模起来后升级企业认证和正式容量方案。

个人开发者配额、QPS 和接口归类可能由高德调整，不能把第三方回答当成永久常量。管理端平台计数用于趋势和异常预警，高德控制台用于官方扣量、限额和超限判断。

## 八、模块边界

- `TutorPlatform/parser/`：订单切割、分类和字段识别。
- `shared/`：Node 与 Worker 共用的去重、导入清洗、评分、异常判断和保留期规则。
- `TutorPlatform/public/`：网页 UI 与交互，不实现解析或高德业务规则。
- `TutorPlatform/server.js`：本地 Node 后端，主要用于快速开发与回归测试。
- `cloudflare/worker.js`：正式站 API、权限、导入编排、高德代理和定时任务。
- `cloudflare/storage.js`：Cloudflare D1 数据访问层。
- `cloudflare/amap-service.js`：服务端唯一的高德 Web 服务实现，包含缓存、并发和调用计数回调。
- `clipboard_bridge/`：低耦合兼容增强器，不是网站运行前提，当前产品方向基本弃用 EXE。

## 九、数据、密钥与隐私

- 正式业务数据存储在 Cloudflare D1 `shenzhen-tutor-prod`。
- 本地开发数据存储在 `TutorPlatform/data/db.json` 或 `TUTOR_DATA_DIR` 指定目录。不要覆盖、删除或提交真实用户数据。
- 浏览器偏好和匿名设备 ID 存在 `localStorage`；临时会话令牌存在 `sessionStorage` 或 HttpOnly Cookie。
- 发单申请存储称呼、用户主动填写的微信号/手机号、审核状态和时间。普通列表不公开联系方式。
- 管理员凭证经过客户端派生和服务端 Pepper 保护；真实密钥只保存在 Cloudflare Worker Secret、本地 `.dev.vars` 或被 Git 忽略的 `.env.local`。
- 禁止把真实密钥、Token、私人手机号、真实订单数据、截图或导出 SQL 提交到 Git。页面明确要求公开展示的平台联系人除外。
- 不得在未授权时部署其他公网环境、重置数据库、替换密钥或执行破坏性迁移。

## 十、正式部署与发布约定

- GitHub：`https://github.com/lzhdelife/shenzhen-tutor-web`
- 稳定分支：`main`
- Cloudflare Worker：`shenzhen-tutor-web`
- 正式数据库：D1 `shenzhen-tutor-prod`
- 正式域名：`https://tutor.liuzonghao.top`
- 配置入口：`wrangler.jsonc`

用户当前约定：代码改动完成后运行测试、提交、推送 GitHub，并部署正式站供其直接测试。纯文档改动无需部署 Worker。涉及 D1 migration 时，必须先完成测试，再应用远端迁移，最后部署 Worker。

标准验证与发布顺序：

```powershell
npm.cmd test
npm.cmd run cloudflare:test
npm.cmd run check:secrets
git diff --check
npx.cmd wrangler d1 migrations apply shenzhen-tutor-prod --remote
npm.cmd run cloudflare:deploy
```

没有新 migration 时不要为了形式重复修改数据库。部署后检查正式域名的静态页面、核心 API、手机布局和与本次改动直接相关的真实交互。提交应清晰；推送或部署失败必须明确报告，不能掩盖。

## 十一、稳定性取舍与已删除功能

- 保留：人工发单审核、粘贴/TXT 导入、队列反馈、去重、三天清理、列表/地图、地点候选、直线距离、路线、异常复核和核心管理删除。
- 已移除：普通用户登录门槛、问题反馈、平台公告、平台设置、网页端 EXE 高频轮询、复杂浏览器返回历史、订单重新发布/下架/成交/开放/关闭、申请人数展示。
- 兼容但不主动运行：剪贴板桥接服务端 API 和旧公告数据结构。旧接单申请写入接口和数据表已删除；当前“申请接单”只按需读取订单原文和联系方式。
- 谨慎扩展：实时通信、第三方统计 SDK、AI 在线解析、大型报表、多账号高德 Key 轮换。没有明确收益、合规边界和容量方案时不引入。

## 十二、新窗口接管步骤

1. 进入仓库，完整阅读本文件。
2. 检查 `git status --short --branch`、`git log -5 --oneline`，确认当前 `main` 和 `origin/main` 状态。
3. 阅读与具体任务相关的代码、测试和专项文档，不依赖旧聊天记忆，也不要只根据本文猜实现。
4. 修改前确认工作区，保留用户数据、密钥和已有改动；只做用户明确提出的变化。
5. 修改后运行与风险相称的自动测试、真实浏览器验收和 `git diff --check`。
6. 除非用户明确改变约定，代码改动完成后提交、推送 GitHub并部署正式站；纯文档不部署。
7. 若某项功能会明显拖慢首屏、增加持续请求、扩大隐私面或让交互变得难以理解，应先说明影响并给出删减建议。
