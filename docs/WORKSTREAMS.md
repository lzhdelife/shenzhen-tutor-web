# 并行开发与协同规则

## 目标

项目允许用户直接在任一子任务提出局部要求，同时保证字段、接口、测试和最终产品保持一致。协同不依赖聊天上下文，而依赖仓库中的契约、交接文件和 Git 提交。

## 当前工作流

| 工作流 | 分支 | 负责范围 | 不负责 |
| --- | --- | --- | --- |
| 主任务 / 集成 | `codex/web-first-rebuild` | 架构、公共契约、本地运行、账号、订单、页面、最终集成 | 不在多个位置重复解析或地图逻辑 |
| 剪贴板桥接 | 主任务内独立提交 | Windows 剪贴板监听、本机历史、断网重试、网站连接、EXE 打包、`/api/clipboard/*` 契约 | 解析规则、高德逻辑、订单字段判断 |
| 文本解析 | `codex/parser-accuracy` | 无损切割、字段提取、证据、置信度、解析回归 | 高德网络调用、登录、数据库实现 |
| 地点与路线 | `codex/amap-location-integration` | 高德候选、用户确认、标准地址、经纬度、路线距离 | 文本解析正则、登录、页面整体视觉 |

账号/本地数据、订单页面、PC Web 布局、发布与部署验收仍由主任务负责。剪贴板桥接器保持小而独立，只负责把原文可靠送到网站；网站继续通过统一 `/api/parse` 和 `/api/import` 完成业务。当前不做移动端专项验收；当其他模块出现一组可独立验收的需求时，再创建短期专项任务，避免任务过多导致接口漂移。

## 稳定边界

```text
Web 页面
  -> HTTP API
     -> AccountService
     -> OrderService -> OrderRepository
     -> ParserService
     -> LocationService
```

- `ParserService` 输入原始文本，输出订单草稿、原文跨度、证据和置信度；不写数据库，不调用高德。
- `LocationService` 输入解析出的地点查询和行政区提示，输出候选；确认后输出标准地址、经纬度和提供方证据；不解析整段订单文本。
- `OrderService` 负责预览确认、导入、去重、状态和权限；它通过接口调用解析与地点服务。
- `OrderRepository` 负责数据存取。本地实现和将来的云端实现共享同一业务接口。
- Web 页面只展示和提交契约字段，不拥有解析正则、高德 Key 或数据库规则。

## 用户直接向子任务提要求时

1. 子任务先判断要求是否完全属于自己的负责范围。
2. 范围内改动直接实现、测试并提交到自己的分支。
3. 涉及共享字段或 API 时，同步更新契约文档和 `docs/handoffs/<stream>.md`。
4. 涉及其他工作流时，不跨界复制实现；在交接文件中写明依赖、期望输入输出和待集成事项。
5. 主任务最终读取交接文件、审查提交和契约测试，再完成集成。

## 完成交接格式

每个子任务创建或更新自己的交接文件，至少包括：

```text
分支与基线提交
负责和修改的路径
新增或修改的接口/字段
测试命令与结果
最终提交哈希
已知风险和未完成项
主任务集成顺序
```

没有交接文件、契约说明或通过的领域测试，主任务不合并该子任务。
